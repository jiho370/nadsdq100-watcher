# MAINTENANCE.md — 이 리포를 고칠 때 참고할 것

`LIVE.md`/`HISTORY.md`가 "무슨 전략인지"를 다룬다면, 이 문서는 **"이 리포를 어떻게
편집·리팩터링·동기화할지"**다. 전부 실제로 이 리포에서 사고가 났거나 사고가 날 뻔했던
사례에서 나온 규칙이다 — 추상적 모범사례가 아니라 여기서 검증된 것만 적는다.

---

## 1. 문서는 숫자를 소유하지 않는다

값(비용률·세율·가중치·임계값)을 문서·주석에 직접 적지 말고 **정의된 코드 위치를 가리켜라.**

- **실제 사례**: `backtest_kr_core.py` docstring이 "코스피 0.15%"라고 적어놨는데 실제 상수
  (`KR_SELL_TAX`)는 0.20%였다. 코드는 상수에 위임해 동작은 멀쩡했지만 주석만 거짓말을 했다.
- **실제 사례**: 코인 비용 30bp→5bp 정정이 한 파일 주석에만 기록되고 9개 스크립트로
  전파되지 않았다.
- **적용**: 문서에 "왕복비용 33bp"라고 쓰지 말고 "왕복비용은 `backtest_costs.KR_SELL_TAX`
  참고"라고 써라. 숫자가 필요하면 그 시점에 코드를 실행해서 뽑고, "n월n일 실측 스냅샷"이라고
  날짜를 박아라.

## 2. "현재 상태"를 문서에서 베끼지 마라 — 코드에서 다시 확인해라

기존 문서(심지어 "현재 라이브 스냅샷"이라고 적힌 표조차)를 신뢰하지 말고, env 기본값·딕셔너리
리터럴을 직접 grep해서 검증해라.

- **실제 사례**: `SYSTEM_OVERVIEW.md`가 한국 개별주 점수공식을 옛 모멘텀 공식으로 적어뒀는데
  실제로는 2026-07-14에 밸류×배당(`valuediv`)으로 전면 교체돼 있었다. 미국/한국 매도규칙도
  "트레일링 -20% 활성"이라고 적혀 있었지만 실제 기본값은 `SELL_TRAIL=0`(비활성)이었다.
- **적용**: "지금 뭐가 라이브인지" 쓰기 전에 반드시 `grep -n 'os.environ.get('` 등으로 실제
  기본값을 확인해라. 문서끼리 대조하지 말고 코드와 대조해라.

## 3. 파일을 옮기거나 이름을 바꿀 때

1. **거꾸로 참조하는 게 있는지 먼저 확인**: `grep -rl <모듈명>` — 리프 노드인지 확인 후 이동.
   (`research/` 재편 때 8개 전부 리프인지 먼저 확인하고 옮겼다.)
2. **전체를 훑어서 옛 이름을 찾아라 — 이동 대상 자신도 포함해서.** 첫 훑기에서 이동/이름바꿀
   파일 자체를 제외하고 검색하면, **그 파일 내부의 자기참조**를 놓친다.
   - **실제 사례**: `STRATEGY.md`→`HISTORY.md` 리네임 때 46개 파일 107건은 기계적으로
     치환했는데, `HISTORY.md` 자기 자신 안의 9개 자기참조("이 STRATEGY.md는...")를 처음엔
     빼놓고 안 고쳐서 새로 만든 파일이 자기 옛 이름을 부르고 있었다.
3. **상대경로 import는 문자열 치환이 위험하다** — `research/` 스크립트를 옮길 때 다른 스크립트가
   `from research.crypto.X import`처럼 점 경로로 참조하고 있으면, 이동 후 그 점 경로도
   같이 고쳐야 한다. `sed`로 일괄 치환하다가 `from X import` 구문에서 `import` 토큰까지
   먹어버린 적이 있다(정규식 lookahead 없이 공백만 보고 자르면 발생) — 치환 후 반드시
   `compileall`로 문법 검증.
4. **이동 후 검증은 3단계**: `python -m compileall`(문법) → 점 경로 import를
   `importlib.util.find_spec`로 전수 확인(연결성) → 자산군별 대표 모듈 1개씩 실제
   `import`(런타임 부작용 확인). 세 번째를 건너뛰면 "정의는 있는데 import 시점에 죽는" 걸
   못 잡는다.

## 4. git 동기화 — 이 리포는 3자가 동시에 쓴다

GitHub Actions(주 3~4회+워치독), 로컬 PC 작업 스케줄러(pregen), 그리고 이 세션. 푸시 전에
항상 이 순서:

1. `git fetch origin main` → `git rev-list --count HEAD..origin/main`로 뒤처짐 확인.
2. **뒤처져 있으면 rebase 전에 사용자의 미커밋 WIP를 스태시로 보호**
   (`git stash push -u -m "설명"`) — 스태시 안 하고 rebase 시도하면 "unstaged changes"로 막힌다.
3. `git rebase origin/main`. 충돌 나면 **원격이 상태파일(commit-back)이면 원격을, 내 작업이면
   내 것을 채택**하되 근거를 확인해라(다음 항목 참고).
4. compileall + import 재검증 (구조를 옮긴 리베이스라면 특히).
5. `git stash pop`으로 사용자 WIP 복원.
6. push.
- **실제 사례**: KOSPI200 캐시 merge driver 작업과 리포 정리가 같은 파일을 건드려 리베이스
  10개 커밋이 자동 충돌 해소됐다(merge driver를 로컬에 등록해뒀기 때문) — driver를 등록 안
  했으면 전부 수동 충돌이었을 것.

## 5. `state/*.json`은 실거래 데이터다 — 로컬 diff를 함부로 믿지 마라

리베이스/스태시 과정에서 `state/ai_holdings.json` 같은 파일에 로컬 미커밋 변경이 보이면,
**그게 내가 의도한 편집인지부터 의심해라.** 오래된 스태시가 나중에 pop되면서 새 HEAD 위에
옛 값을 얹는 경우가 실제로 있었다(`peak: 75.40`이 로컬에 남아있었는데 원격은 이미
`peak: 78.47`로 갱신돼 있었다 — 스태시 팝 잔여물이었다).

- **판단 기준**: `last_run`/`as_of` 날짜가 더 최신인 쪽, 또는 값이 "더 많이 진행된" 쪽
  (peak는 오르기만 함, 날짜는 앞으로만 감)을 원본으로 신뢰해라.
- **의심되면**: `git checkout -- <파일>`로 HEAD(=리베이스 후 origin) 버전을 그대로 채택하고
  로컬 diff는 버려라 — 이 파일들은 "내 편집"이 아니라 "자동화가 쓴 결과"이기 때문에
  손으로 고칠 이유가 없다.

## 6. PowerShell 스크립트(`scripts/*.ps1`) 함정 셋

1. **`Register-ScheduledTask` 같은 cmdlet은 실패해도 '비종료 오류'**라 스크립트가 다음 줄로
   그냥 넘어가고, 그 뒤의 "등록 완료" 메시지가 무조건 출력된다. `-ErrorAction Stop` +
   try/catch로 승격시켜야 실패가 실패로 보인다. (`register_pregen_task.ps1` 등 3개에서 실측:
   `Access is denied`가 떴는데 "Registered:"도 같이 찍혔다.)
2. **한글이 든 `.ps1`은 UTF-8 BOM이 없으면 PowerShell 5.1이 시스템 ANSI(CP949)로 잘못
   읽어 구문이 깨진다.** 문법 자체는 멀쩡해도(UTF-8로 읽으면 오류 0) 실행 시점에 깨진다.
   수정 후 검증은 `[System.Management.Automation.Language.Parser]::ParseFile`을
   **기본 인코딩**으로 호출해서 확인해라(명시적으로 UTF-8 디코딩해서 검사하면 이 버그를 놓친다).
3. **파이프(`cmd 2>&1 | Out-File`)는 `$LASTEXITCODE`를 스크립트 자신의 종료코드로 자동
   전파하지 않는다.** 외부 명령 직후 바로 `$LASTEXITCODE`를 변수에 담고, 실패 시
   `exit $code`로 명시해야 작업 스케줄러의 "마지막 실행 결과"가 진실을 반영한다.
   (`trigger_report.ps1`이 `gh workflow run` 실패를 항상 종료코드 0으로 감추고 있었다.)

## 7. "부분 실패를 조용히 전체 성공으로 보고"하는 안티패턴

여러 항목을 순회하며 개별 실패를 로그만 남기고 넘어가는 함수(`for ... try/except: log`)는,
**호출부가 "몇 개 실패했는지"를 알 방법이 없으면** 위험하다 — 100% 실패해도 빈 결과를 정상
반환값처럼 돌려주고, 호출부는 그걸로 "완료" 상태(예: `profiles_updated=오늘`)를 찍어버린다.

- **실제 사례**: `gen_profiles._run_cli`가 실패한 요청을 결과 dict에서 빠뜨리기만 해서,
  CLI가 100% 실패해도 메타데이터엔 "오늘 갱신됨"이 찍히고 종료코드는 0이었다.
- **점검 포인트**: 이런 함수를 보면 반환값에 실패 목록/개수가 있는지 확인해라. 없으면
  `(성공결과, 실패목록)` 튜플로 바꾸고, 호출부에서 "성공 0건"과 "일부 실패"를 구분해서
  전자만 `sys.exit(1)`로 드러내라(후자는 보통 자동 재시도로 자연 치유되니 하드 실패로
  취급하면 오히려 노이즈).

## 8. CI가 실제로 commit-back 하는 범위를 확인해라

`.github/workflows/report.yml`의 "Persist state" 단계는 **`state/`만** `git add`한다.
새로 추가하는 파일이 매 실행마다 바뀌는데 `output/`에 있으면, 그 변경분은 영원히 unstaged로
남아 `git pull --rebase`를 막고, 그게 반복되면 다음 실행 자체가 실패한다.

- **실제 사례**: `output/ai_verdict_log.json`이 이 문제로 `git pull --rebase`를 막아서
  국장 메일 중복발송 가드(`last_sent.json` 갱신)가 무력화돼 있었다(`ee6f63f`).
- **적용**: 매 실행마다 바뀌고 계속 추적해야 하는 새 파일은 `state/`에 두거나, `report.yml`의
  persist 단계에 명시적으로 추가해라. 둘 다 안 하면 조용히 쌓이다가 터진다.
